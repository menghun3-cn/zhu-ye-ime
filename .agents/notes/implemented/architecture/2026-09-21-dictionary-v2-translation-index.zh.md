# Agent Note: Dictionary v2 translation index and reverse lookup

Status: implemented

[English](2026-09-21-dictionary-v2-translation-index.md) | 中文

## 问题

FR-005/FR-006/FR-007 要求在输入时提供双语建议：输入法必须在中文候选旁显示译文，并允许用户选择上屏中文词或译文。仅把译文放在词条表里无法独立回答英文到中文的查询；内存翻译表又会让数据契约与词典产物分离。真实词表还需要一条从归一化英文回到中文词的确定性反查路径。

## 决策

词典格式从 v1 升级到 v2（`DICT_VERSION = 2`）。固定头部从 96 字节扩展到 128 字节，内容 SHA-256 存放在头部第 80..112 字节，仍然覆盖头部之后的全部字节。在 bigram 表与文本池之间，v2 新增两个只读有序索引：

```text
Word Translation Index  24 字节/条：中文词文本偏移/长度、译文文本偏移/长度
Reverse Translation     24 字节/条：归一化英文文本偏移/长度、中文词文本偏移/长度
Index
```

`dict_builder::build_v2` 生成确定性字节：词条按拼音分组，文本池去重，bigram 合并，两个翻译索引的数量与偏移都从同一份源数据计算。反查键对英文做小写与空白折叠归一化，因此 `HELLO`、`good morning` 与种子数据中的对应键保持一致。

`DictionaryFile` 在 mmap 记录视图上实现 `Translator`。`zh_to_en` 对中文词索引做二分查询；`en_to_zh` 先归一化查询串，再对反查索引做二分查询。两个查询在索引数量为零时立即返回 `None`，因此没有任何译文的有效词典仍能加载并安全查询。`zhu-ye-dict` 的 build、inspect、verify 命令在加载时校验译文与反查数量、边界与排序；`zhu-ye-cli dict <文件> -r 英文` 提供反查入口供开发调试。

## 曾考虑的替代方案

**仅把译文保留在词条表。** 否决：每次英文到中文查询都必须扫描整张表，无法独立回答反查。有序反查索引让两个方向都保持在二分查询时间，且继续使用同一套 mmap 记录视图。

**把译文放进独立的 JSON/SQLite 表。** 否决：第二套存储会拆散构建与校验路径，引入额外依赖，并破坏保持加载廉价且确定的单一 mmap 字节契约。

**只做正向翻译，不做英文反查。** 否决：FR-007 要求反查，且要容忍大小写与空白差异；归一化键就是构建器、加载器与 CLI 共用的确定性形态。

## 影响

词典产物现在同时携带双语层的两个方向，输入引擎可以复用拼音与 bigram 查询所用的同一个 mmap 文件来驱动译文候选层。新索引在加载时被校验，空译文集仍是合法词典状态。测试覆盖文件往返、归一化反查键、头部计数篡改，以及 v2 文件驱动的引擎行为。格式消费者必须按 `DICT_VERSION = 2` 加载；v1 文件不再可加载。
