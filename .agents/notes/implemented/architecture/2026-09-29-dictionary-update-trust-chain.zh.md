# Agent Note: 词典更新信任链与更新器进程

Status: implemented

[English](2026-09-29-dictionary-update-trust-chain.md) | 中文

## 问题

M6-P 交付了 manifest，M6-R 让多个包可在运行时加载，但没有任何机制能把包送到用户机器上。
FR-020 要求发现、下载、完整性校验、原子替换与回滚，并且受一条硬约束：在线更新属于在线
功能，必须**默认关闭**（P-03、NFR-010）。

两个性质使它不只是复制文件的问题：

1. **词典包就是攻击面。** 包会被 mmap 并在每次按键时查询。接受被篡改的包意味着攻击者
   控制了候选文本。仅靠内容哈希不构成信任锚——能改写包的人也能改写旁边的哈希。
2. **TSF DLL 绝不能碰网络。** 它运行在宿主进程内（记事本、浏览器、IDE）。在那里做阻塞
   或失败的 TLS 握手可能挂起宿主、触发杀软启发式判断，或让候选生成卡住。

## 决策

### 信任锚：编译内置的公钥

manifest 携带 ed25519 签名。关键在于，验签使用**编译进客户端**的公钥，而不是 manifest
里内嵌的 `public_key` 字段：

- `verify_signature_with_key(manifest, trusted_key)` 是更新器与
  `zhu-ye-dict verify-signature` 共用的验签入口。
- `verify_signature(manifest)`（自包含、用内嵌公钥）只用于审计与诊断。

内嵌公钥仍写入 manifest，便于发布方轮换密钥、也便于运维比对"发布的内容"与"客户端信任
的内容"。有一项测试用攻击者密钥签名 manifest，先确认自包含校验通过（伪造物内部自洽），
再断言内置公钥拒绝它。没有这项测试，该设计距离信任攻击者提供的密钥材料只差一行。

### 签名对象是规范化 JSON，不是文件字节

`canonical_bytes` 以 `signature: None` 与紧凑格式序列化 manifest。对原始文件字节签名会在
任何重新格式化时失效；而把签名块**包含在内**签名则是自指。排除签名字段使签名幂等且对格式
不敏感；有一项测试断言附加签名前后规范化字节完全相同。

### 失败原子性

`update.rs` 实现：验签 → 逐包校验 SHA-256 与大小 → 写入 `packs/staging/` → 逐个包原子替换
（写同目录 `*.zyct.new` 再 `rename`）→ 删除 staging。旧包先复制为 `.bak`，
`rollback_pack` 可恢复。

同一卷内的 `rename` 是原子的，因此应用过程中崩溃只会留下旧包或新包，绝不会是截断文件。
任何失败都保留旧包并报告原因；各包独立应用，一个坏包不阻塞其他包。已安装哈希与目标一致的
包直接跳过，不下载也不备份。

### 只有可分发的包参与

`DISTRIBUTABLE_PACK_IDS = ["it", "med", "slang"]` 限定更新器会拉取的范围。基础包随安装器
只读交付，`real`/`seed` 是开发产物、从不发布。这不是理论顾虑：第一次针对含全部六个包的
真实 manifest 做端到端运行时，它尝试下载 `base.zyct` 并以 HTTP 404 失败。

因此 `verify_release` 只校验**下载集合中实际存在的包**，而不是 manifest 列出的每一个包。
签名仍针对完整、未修改的 manifest 校验——早先一次"先裁剪 manifest 再调用 `apply_release`"
的尝试破坏了验签，因为裁剪包列表会改变规范化字节。

### 独立进程、默认关闭

`zhu-ye-updater` 是独立二进制，也是唯一执行网络 I/O 的组件（S-4）。它在一次操作后退出，
不留下常驻进程。

默认关闭在配置层强制：`online_update: false` 时，`check` 与 `apply` 在构造任何请求之前
就返回。验证方式是把 manifest URL 指向不可达地址——命令仍然成功退出且不发起网络尝试，
若真在建连则不可能如此。

下载通过系统自带 `curl.exe`（Windows 10+ 均存在）完成，而不链接 HTTP/TLS 栈。这使更新器
的依赖面仅剩 `ed25519-dalek`。

### 密钥处理

签名工具从 `ZHU_YE_RELEASE_SECRET_KEY` 读取私钥，且从不接受命令行参数——那会让私钥暴露在
进程列表与 shell 历史中。客户端公钥经构建期 `ZHU_YE_RELEASE_PUBLIC_KEY` 注入。未内置公钥
时，更新器拒绝应用任何内容，而不是回退到未校验路径。

## 曾考虑的替代方案

**信任 manifest 内嵌的公钥。**
否决：能提供 manifest 的攻击者也能提供自己的公钥与签名，签名就成了装饰。内置公钥才是让
篡改可被发现的东西。

**对 manifest 文件字节签名。**
否决：这会把签名有效性绑死在 JSON 格式上，任何工具步骤重新序列化 manifest 都会让合法签名
失效。

**只校验内容哈希，不签名。**
否决：哈希与载荷在同一份文档里，对控制下载的攻击者毫无保护。

**在 TSF DLL 内下载。**
按 S-4 明确否决：在宿主进程内做阻塞网络工作有挂起宿主、卡住输入的风险，DLL 也不该持有
TLS 状态。

**把 HTTP 客户端 vendor 进更新器。**
否决：`curl.exe` 在每个受支持的 Windows 版本上都已经存在，避免 TLS 栈能让更新器的依赖
与审计面保持最小。

**逐个应用包并在首个失败处停止。**
否决：各包独立版本化、独立有用；一个失败不该阻塞其他包，且每个失败本身已经保留了对应的包。

**直接写目标文件，不用 staging + rename。**
否决：写入过程中崩溃或断电会留下截断的 `.zyct`，加载器随后会在启动时拒绝它——用户会因为
一次失败的更新而失去一个可用包。

## 后果

- 更新端到端经过认证：对规范化 JSON 的签名，加上逐包内容哈希。两者都通过之后才有字节进入
  包目录。
- 成本：轮换发布密钥需要发一个新引擎版本，因为信任锚是编译内置的。manifest 携带
  `min_engine_version`，因此可以告知旧客户端跳过它无法校验的包。
- 成本：分发包是一份硬编码列表。新增可分发包需要改代码并更新测试，而不只是改 manifest——
  这是刻意的，使"发布一个新包"成为一个显式决策。
- 成本：更新器依赖 `curl.exe`。在缺失或被拦截的系统上，更新会明确失败；输入不受影响。
- `zhu-ye-dict` 的 manifest 类型现在来自 `zhu-ye-core`，构建侧与运行时侧不会在传输格式上
  漂移。
- `ed25519-dalek`（BSD-3-Clause）登记在 `docs/licenses.md` 新增的代码依赖一节，因为它是
  第一个密码学依赖。
- 测试：13 项 manifest 与 12 项 update 单测，外加两项更新器默认关闭断言；工作区共 317 项。
  九个验收场景在本地静态服务与隔离的 `APPDATA` 沙箱上端到端跑通：正常更新、重复 apply
  空操作、已装包被篡改后恢复、签名篡改被拒、截断包被拒、manifest 不可达、版本门槛、
  默认关闭零网络、无驻留进程。
