# Agent Note: v0.1.2 GA release execution and troubleshooting (FR-061~063, T-096~T-099)

Status: implemented

English | [中文](2026-10-05-release-v0.1.2.zh.md)

## Problem

v0.1.2 (alpha removed) is the first **GA** release: version lock → release branch →
PR into main → tag → release.yml full pipeline (seven assets) → upstream feed →
website wording. It took four CI runs to succeed (runs 37289789026 /
37290578197 / 37291534406 / 37292329820). This note records the release
execution, root causes of the three CI failures, and follow-up actions for
future releases.

## Decision

### Scope of the version lock (PR #103)

- Version: `Cargo.toml` workspace 0.1.2-alpha → 0.1.2; `Cargo.lock` synced via
  `cargo generate-lockfile` (`cargo metadata --no-deps` does not refresh member
  version rows).
- CHANGELOG: the `[0.1.2-alpha] - 2026-10-04` section was folded into
  `[0.1.2] - 2026-10-05` (GA date), appending the batch-3 six items merged on
  2026-10-05 (T-101~105) plus the four release-closure items (T-096/097/098/107);
  `[Unreleased]` stays empty.
- All six site pages' footer-status/hero-note/agents.txt/llms.txt wording moved
  to GA; the download page got exe/zip/SHA256SUMS direct links pointing at
  `releases/download/v0.1.2/<asset>` (verified 200 after release).

### CI failure 1: CC-CEDICT monthly update pin drift (run 37289789026)

- Symptom: fetch-sources step failed with `cedict: hash mismatch: expected
  FD16B26F…, actual 545476AF…`.
- Handling: re-downloaded the upstream URL locally and confirmed the hash
  matches CI (no transport corruption) → decompressed: 125,223 lines, License
  header intact, spot-check shows recent words (躺平/元宇宙), no anomalous
  bytes → relocked `data/pins/cedict.json` (sha256/size/note; PR #104) →
  **deleted then re-created the tag to trigger a new run**.
- Lesson: CC-CEDICT updates monthly; the relock flow is "verify content →
  update pin → delete/re-create the release tag"; re-pushing an existing tag
  does not trigger the workflow.

### CI failure 2: stale `$LASTEXITCODE` after `& script.ps1` (run 37290578197)

- Symptom: `生成发布说明失败` thrown while the log shows RELEASE_NOTES.md was
  written (2295 chars).
- Root cause: the workflow invokes `& ./scripts/release-notes-from-changelog.ps1`
  inline; PowerShell scripts do not update `$LASTEXITCODE` unless a native
  command ran, so the check read the **previous native command's stale code**.
- Fix: explicit `exit 0` on success and `Write-Error + exit 1` on failures in
  the script (PR #105), making the caller's `$LASTEXITCODE` check reliable.

### CI failure 3: environment-level release create failure + Draft state (run 37291534406)

- Symptom: create's stderr swallowed by `2>$null`; `gh release upload` then
  reported `release not found` (create actually left a Draft).
- Handling: a manual `gh release create v0.1.2 --latest` succeeded from this
  host (proves it is not a config problem); with the release existing, run4's
  idempotent create failure was ignored and `gh release upload --clobber`
  filled all seven assets; finally `gh release edit v0.1.2 --draft=false
  --latest` published it.

### Upstream feed (FR-062)

- No `ZHU_YE_UPDATES_TOKEN` on the main repo → CI `publish-updates` warns and
  skips (by design; does not block the main release).
- feed-v0.1.2 **published manually**: downloaded manifest + it/med/slang from
  the main release → `gh release create feed-v0.1.2 --repo
  menghun3-cn/zhu-ye-updates --target <mirror main tip>` (cross-repo target
  must be an object in the mirror repo) + upload --clobber; no prerelease flag
  → latest semantics take over from feed-v0.1.2-alpha.
- Verification: mirror `releases/latest/download/manifest.json` 200 and
  byte-equal to the main release asset; direct links (exe/zip/SHA256SUMS)
  HEAD 200 with matching sizes; verify-site-live all PASS.

### Wrap-up

- main → develop sync hit a site/* conflict (stale dev wording vs GA version);
  resolved with `--theirs` (site wording follows the release branch).
- §17.5 checklist 6/6 checked; §17.6 17.1 exe-asset and 17.2 feed rows
  backfilled; todos T-096~T-099 marked completed.

## Consequences

- GA release v0.1.2 is live with seven assets and correct latest semantics;
  the upstream feed v0.1.2 is live and byte-consistent with the release.
- Three failure modes are documented with root causes; the PowerShell
  `$LASTEXITCODE` pitfall is fixed at the script level and the pitfall pattern
  documented for future CI audits.
- Remaining: ① CI auto feed publishing needs a `ZHU_YE_UPDATES_TOKEN` from the
  user; ② VM silent install/overwrite/uninstall e2e waits for the VM channel
  (T-107 scripts ready); ③ language bar "中/英" visual check waits for a real
  logged-in client (T-100).

## Alternatives considered

- **Tag delete/recreate vs force-push**: re-pushing an existing tag is ignored
  by GitHub Actions, so delete + recreate was chosen to reliably re-trigger
  the workflow. Force-pushing tags is also possible but delete/recreate is
  the documented, least-surprise path.
- **Manual release creation before re-run**: after the create failure, manually
  creating the release first let the next run's upload `--clobber` fill it
  directly, avoiding another full CI cycle just to diagnose the create. This
  worked because the upload step is idempotent by design.
- **Rejecting stale `$LASTEXITCODE` by wrapping in `pwsh -File`**: considered
  changing the workflow invocation to a child process (which gets a real exit
  code), but the minimal script-level `exit 0/1` fix keeps the inline style
  used by the rest of the workflow and fixes all callers at once.
