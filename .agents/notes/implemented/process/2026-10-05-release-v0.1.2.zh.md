# Agent Note: v0.1.2 正式发布执行记录与排障（FR-061~063，T-096~T-099）

Status: implemented

[English](2026-10-05-release-v0.1.2.md) | 中文

## 问题

v0.1.2（去 alpha 定版）为首个**正式版**发布：需经定版 → release 分支 →
PR 合 main → tag → release.yml 全链（七资产）→ 更新源 feed → 官网口径，
全程 4 轮 CI 排障后才成功（run 37289789026 / 37290578197 / 37291534406 /
37292329820）。本 note 记录发布执行细节与三个 CI 故障的根因。

## 决策

### 定版范围（PR #103）

- 版本：`Cargo.toml` workspace 0.1.2-alpha → 0.1.2；`Cargo.lock` 经
  `cargo generate-lockfile` 同步（`cargo metadata --no-deps` 不会刷新
  members 版本行）。
- CHANGELOG：`[0.1.2-alpha] - 2026-10-04` 段并入 `[0.1.2] - 2026-10-05`
  （定版日），补 2026-10-05 合入的批三六项（T-101~105）与发布收尾四项
  （T-096/097/098/107）条目；`[Unreleased]` 保持空。
- 官网六个页面 footer-status/hero-note/agents.txt/llms.txt 状态行全部切
  正式版口径；下载页 exe/zip/SHA256SUMS 直链指向
  `releases/download/v0.1.2/<asset>`（发布后实测 200）。

### CI 故障 1：CC-CEDICT 月度更新 pin 漂移（run 37289789026）

- 现象：fetch-sources 步骤 `cedict 失败：哈希校验失败：期望 FD16B26F…，
  实际 545476AF…（源内容已变化，人工审查 pin 后重锁）`。
- 处置：本地下载上游 URL 复核哈希与 CI 报告一致（传输无损）→ 解压检查
  125,223 行、头部 License 注释正常、抽查含躺平/元宇宙等近年新词条、
  无异常字节 → `data/pins/cedict.json` 重锁（sha256/size/note 追加二次
  重锁记录，PR #104）→ **删 tag 后重打同名 tag 触发新 run**。
- 教训：CC-CEDICT 每月更新，重锁流程即「复核内容 → 更新 pin → 发布层
  删/重打 tag」；重复 push 同一 tag 不触发 workflow。

### CI 故障 2：`& script.ps1` 后 `$LASTEXITCODE` 残留误判（run 37290578197）

- 现象：`生成发布说明失败` 抛错，但日志显示 RELEASE_NOTES.md 已成功写出
  2295 字符。
- 根因：workflow 以 `& ./scripts/release-notes-from-changelog.ps1` 内联
  调用；PowerShell 脚本成功路径不更新 `$LASTEXITCODE`（只在运行 native
  命令后更新），检查读到**上一个 native 命令的残留退出码**。
- 修复：脚本成功路径显式 `exit 0`，异常路径 `Write-Error + exit 1`
  （PR #105）；调用方 `if ($LASTEXITCODE -ne 0)` 变得可靠。

### CI 故障 3：release create 环境性失败 + Draft 状态（run 37291534406）

- 现象：create 的 stderr 被 `2>$null` 吞掉，`gh release upload` 报
  `release not found`（create 实际留下一个 Draft）。
- 处置：本机手动 `gh release create v0.1.2 --latest` 一次成功（证明非
  配置问题）；release 已存在后，run4 中 create 幂等失败被忽略、upload
  `--clobber` 直接补齐七资产；完成后 `gh release edit v0.1.2
  --draft=false --latest` 发布。

### 更新源 feed（FR-062）

- 主仓无 `ZHU_YE_UPDATES_TOKEN` → CI `publish-updates` 告警跳过（设计
  如此，不阻塞主发布）。
- feed-v0.1.2 **手动补发**：从主仓 release 下载 manifest+it/med/slang →
  `gh release create feed-v0.1.2 --repo menghun3-cn/zhu-ye-updates
  --target <镜像仓 main tip>`（跨仓 target 必须是镜像仓内对象）+ upload
  --clobber；无 prerelease 标记 → latest 语义接管原 feed-v0.1.2-alpha。
- 验证：镜像 `releases/latest/download/manifest.json` 200 且与主仓资产
  逐字节一致；直链（exe/zip/SHA256SUMS）HEAD 200 字节数一致；
  verify-site-live 全 PASS。

### 收尾

- main → develop 同步含一次 site/* 冲突（develop 侧旧状态行 vs 发布版），
  采用 `--theirs` 取发布版（site 以发布分支为权威）。
- §17.5 清单 6/6 勾选、§17.6 17.1 exe 资产项/17.2 feed 记录回填、
  todos T-096~T-099 状态已完成。

### 更新源 feed 自动发布启用（2026-10-05 13:53，T-098 闭环）

- 主仓配置 `ZHU_YE_UPDATES_TOKEN` Actions secret（用户 `GH_PAT`，
  fine-grained：Repository access 到 menghun3-cn/zhu-ye-updates +
  **Contents: Read and write**——仅勾选仓库访问为只读，需在 Permissions
  分区显式开写权限）。写权限探针（上传临时 asset 再删除）→ OK。
- 复验中发现并修复两个 workflow 缺陷（PR #112）：①版本源统一读
  `Cargo.toml`——dispatch 触发时 `github.ref_name` 是默认分支名，upload
  步骤曾找 `target/release-assets/develop` 而失败；②publish-updates 去掉
  `--target $sha`——主仓 commit 非镜像仓对象，将来 feed tag 尚不存在时
  create 会 404（被吞）而 upload 报 `release not found`。
- 幂等验证走 `workflow_dispatch`（upload=true，不碰 tag，避开下述删 tag
  副作用）：run 37319495220 全 15 步绿；`publish-updates` success；镜像 4
  资产 `updated_at=13:53:25`、SHA-256 与主仓 release 资产逐项 EQUAL。
  此后每次 `v*` 正式发布自动同步 feed。
- 删/重打 tag 陷阱（已注 create 步骤注释）：删除 tag 会把关联 release
  降级为 untagged + **draft**（GitHub 行为），重跑中 create 幂等失败不会
  自动恢复；恢复方式 = 对 release 做 PATCH（重挂 `tag_name`、
  `draft=false`、`prerelease=false`）。

## 后果

- v0.1.2 正式版已上线：release 七资产、latest 语义正确；更新源 feed
  v0.1.2 在线且与 release 资产逐字节一致。
- 三个故障模式均已记录根因：PowerShell `$LASTEXITCODE` 陷阱已在脚本层
  修复，陷阱模式已文档化供后续 CI 审查。
- **CI 自动 feed 发布已启用并实证通过**（见决策节）；后续发布无需手动
  补发 feed。
- 遗留：①VM 静默安装/覆盖/卸载实测待 VM 通道（T-107 脚本就绪）；②语言栏
  「中/英」目视待真实登录态客户端（T-100）。

## 备选方案

- **删/重打 tag vs force-push**：GitHub Actions 忽略对已存在 tag 的重复
  push，故选删除+重建以可靠重触发；force-push tag 也可行，但删/重建是
  已文档化的最不易误路径。
- **重跑前手动建 release**：create 失败后先手动建 release，使下一 run 的
  upload `--clobber` 直接补齐，省去为诊断 create 而完整重跑 CI 的成本；
  因 upload 步骤按设计幂等而成立。
- **改用 `pwsh -File` 子进程获取真实退出码**：曾考虑改 workflow 调用方式，
  但脚本级 `exit 0/1` 最小修复保持全 workflow 内联风格一致，且一次修复
  所有调用方。
