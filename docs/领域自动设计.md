## 3. 总体架构

全部逻辑落在 `zhu-ye-core`（纯算法）与 `zhu-ye-ime` 引擎（候选组装），TSF 层**零改动**
（领域提权只影响候选内容与顺序，候选窗展示/选词/上屏交互全部复用既有路径）。

- **识别（FR-033）**：输入帧候选择优完成后，从组合串拼音切分结果中取"完整词"（与主
  候选同源的切分词），对**已启用**的领域包 id（字典序）逐个做完整词命中检测：
  命中即记候选领域；第一个命中的包 id 即提权领域（D-16）
- **提权（FR-034）**：把该领域包中的候选（来源仍为领域候选，D-17 不改变来源语义）
  重排到基础候选之后、追加组（缩写/英文/emoji）之前（D-13）；领域候选的文本、译文、
  来源标记不变，仅移动展示位置
- **开关（FR-035）**：`enable_domain_boost`（默认 true）持久化进 config.json（复用
  `pack_config` 原子保存），关闭时走既有追加语义（T-050 基线）

### 3.1 为什么在引擎候选组装层做（而不是改 core 排序内核）

- 领域提权是**展示层策略**，不等同于排序分数调整——改分数会波及 T-057 基准与
  FR-002 确定性测试（两条全量回归面）；组装层重组只影响"清单的顺序"，核心排序
  逻辑（分数、bigram、beam）零触碰
- 提权只作用于"已启用领域包"（P-12 不突破），引擎层天然持有已装配的复合词典

### 3.2 识别输入与"完整词"判定（D-15）

- 输入串拼音切分：复用引擎既有切分结果（`segment_all` 的主切分路径产生的完整音节串，
  同主候选的来源词）；**前缀/不完整音节不参与识别**（D-15）
- 命中判定：对每个启用包 id（按字典序，D-16）调用词典 `lookup`/`lookup_prefix` 的
  完整词查询，命中 >0 即记为候选领域并停止（取首个，字典序保证确定性）

### 3.3 提权位次协调（D-13 与既有追加组）

现有候选清单顺序（从旧到新）：

```
基础候选（拼音主路径，FR-001/002）
└─ 追加：缩写组（FR-017）→ 英文组（FR-030）→ emoji 队尾（FR-029）
```

领域提权后：

```
基础候选
└─ 领域提权候选（D-13：插基础之后、追加组之前）
└─ 追加：缩写组 → 英文组 → emoji 队尾（顺序不回退）
```

- 领域候选 = 从领域包词条子集中取"与当前组合串完整词命中"的候选（来源标记保留），
  同词与基础去重（P-12 合并规则已去重，提权只移动位置不新增条目）
- 无领域命中时清单与现版逐位一致（T-050 不漂移，验收 11.1「无命中不扰动」）

## 4. 接口设计（草案）

core（新增，纯算法，全部确定性可测）：

```
pub enum DomainBoostDecision { None, Domain(String) }   // 识别结果：无 / 首个命中包 id
pub fn detect_domain_boost(
    complete_words: &[&str],                             // 完整切分词（D-15）
    pack_ids: &[&str],                                   // 已启用包 id（字典序，D-16）
    lookup: &dyn Fn(&str) -> usize,                      // 完整词命中计数探针
) -> DomainBoostDecision
```

ime 引擎（候选组装）：

```
pub fn enable_domain_boost(&mut self, on: bool);         // FR-035 开关（默认开）
// refresh_candidates 内：
//  1. 基础候选组装不变
//  2. detect_domain_boost(...) → Domain(id) 时，收集该包完整词命中候选
//  3. 插入点 = 基础候选之后、追加组拼接之前（D-13）
```

配置（`pack_config` 扩展，向后兼容旧配置文件）：

```
"enable_domain_boost": true                             // 缺失时默认 true（D-14）
```

## 5. 测试策略

core 单测（新增，确定性）：
- 识别：单包命中 / 多包按 id 字典序取首个（D-16）/ 无命中 None / 前缀不识别（D-15）
- 提权位次：领域候选插基础之后、追加组之前（D-13，与缩写/英文/emoji 组共存）
- 开关：关闭后恢复追加语义（T-050 基线）、默认开（D-14）
- 确定性：同一输入两次候选顺序逐位一致（FR-002 不回退）

ime 引擎集成测试：
- `jubu`（启用 it 包）→ IT 候选提权可见、基础首候选保持可及
- `nihao` 无领域命中 → 与现版逐位一致
- `xinzang`（仅 base+it）→ 医学包未启用不参与
- 提权不改变选中上屏文本（来源与文本同领域包词条）

host-e2e `--m11` 断言组（验收 11.x）：上述用例落地为可执行断言（host 侧
`--multi-pack` 基底扩展：base+it / base+it+med 两种装配）。

## 6. 性能与隐私

- 识别开销：每帧对启用包做若干次 `lookup`（完整词命中探针），与既有复合词典查询同阶；
  `CompositeDictionary` 热路径快速通道（单包非空短路）直接受益；验收 11.2 单帧 ≤2ms
- 隐私：识别不产生网络请求（NFR-010）；不记录输入内容
- 基准：提权只在命中领域时改变候选顺序；T-057 eval 集（无领域包命中样例）逐位不回退
  （验收 11.2 复跑记录）

## 8. 风险与备选

- **提权误伤**：领域词上移可能让用户在通用场景多按一次选词 → 提权仅在**完整词命中**
  时生效（D-15）且可总开关关闭（D-14），风险可控
- **多领域抖动**：同一串命中不同领域时按包 id 字典序固定（D-16），同一输入永远同结果
- **与追加组冲突**：emeoji 队尾规则（FR-029 队尾追加）不回退 → 提权插入点定在追加组
  **之前**（D-13），追加组整体后移，不改变组内顺序
- **性能**：识别失败路径必须走既有快速通道（单包短路），避免多包串行全扫描；
  bench 增设领域识别场景实测
