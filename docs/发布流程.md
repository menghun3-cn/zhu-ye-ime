# 发布流程（P-01 发布分发闭环，T-094）

> 本文档描述竹叶输入法的可重复发布操作手册：从 develop 集成分支切 release、
> 版本定版、密钥与签名、资产组装、GitHub Releases 上传、更新源验证到发布检查
> 清单核对。属于第十期发布分发闭环（P-01，需求决策 2026-09-28 确认；渠道 =
> GitHub Releases + manifest 分发，镜像配置留待后续）。
>
> Git 层面的发布动作由 `.agents/skills/git-publish/SKILL.md` 执行；本文档覆盖
> 其在制品上传、签名与更新源验证部分（该技能只负责 Git 动作）。

## 2. 发布密钥管理（ed25519，P-04 信任锚）

信任锚机制：`zhu-ye-dict sign-manifest` 用发布私钥对 manifest 的**规范化 JSON** 签名；
客户端更新器内置公钥验签后才下载应用（详见 Agent Note
`.agents/notes/implemented/architecture/2026-09-29-dictionary-update-trust-chain`）。

### 2.1 首次发布：生成密钥对

```powershell
.\target\release\zhu-ye-dict.exe keygen
```

输出 32 字节十六进制 私钥（`ZHU_YE_RELEASE_SECRET_KEY`）与 公钥
（`ZHU_YE_RELEASE_PUBLIC_KEY`）。

- **私钥**：只存在于发布环境（建议放入系统密钥库或受 ACL 保护的文件），**绝不写入
  仓库、提交历史、自动化日志或命令行参数**（命令行参数会留在进程列表与 shell 历史）。
  发布流程在每次打包前从该受保护来源注入环境变量。
- **公钥**：可入库（它是公开材料）；客户端在构建期经环境变量 `ZHU_YE_RELEASE_PUBLIC_KEY`
  编入更新器（`option_env!`）。公钥同时写入每个签名 manifest 的 `signature.public_key`。

### 2.2 轮换与泄露预案

- **轮换**：信任锚编译内置，换钥必须随下一次引擎版本发布（新客户端内置新公钥）；
  旧客户端按 `min_engine_version` 跳过无法校验的新包。
- **泄露**：立即用 `zhu-ye-dict keygen` 生成新对，随下一次引擎发布轮换；在下一次
  发布前，把疑似泄露的私钥从所有它曾出现的环境移除。
- **丢失**：无恢复手段，直接生成新对并轮换（旧客户端会拒绝新包，属预期行为）。

## 3. 发布步骤

以下按顺序执行；每步结束核对产物或状态后再进入下一步。

### 步骤 1 — 版本与分支（git-publish）

按 `.agents/skills/git-publish/SKILL.md` 执行：

```
develop（最新 tip）→ release/vX.Y.Z → PR 合入 main → 打 tag vX.Y.Z → main 同步回 develop → 删除 release 分支
```

- 目标版本号 = 当期定版（格式 `vX.Y.Z` 或带 `alpha`/`beta` 后缀）；
- CHANGELOG 目标版本段的发布日期在此时补全为实际发布日；
- 合并 PR 与打 tag 的顺序硬约束：**先合入 main，再打/推 tag**。

### 步骤 2 — 注入公钥并构建 release 产物

> 本步骤与步骤 3/3.5 **已 CI 化（T-095/T-097/T-098）**：推 tag 后由
> `.github/workflows/release.yml` 自动执行（数据源锁定校验 → CC-CEDICT 解压 → 词典
> 全量构建 → 公钥注入 + 私钥签名 manifest + 复核 → zip/SHA256SUMS → Inno Setup 编译
> exe 安装包 → e2e 全链 → `gh release create/upload` **七项资产**（zip、SHA256SUMS、
> exe 安装包、feed 三包 + manifest）→ 步骤 3.5 发布更新源镜像；版本含 `-` 自动
> prerelease）。**正式发布只需推送 tag**；下述本地 assemble 保留为开发/调试路径
> （含 `workflow_dispatch` 手动试跑默认不上传，`upload` 输入为 true 才上传）。

在发布环境设置两个环境变量后运行（`assemble-release.ps1` 会自动执行）：

```powershell
$env:ZHU_YE_RELEASE_SECRET_KEY = '<私钥 hex>'   # 从受保护来源读取，勿手打在命令历史
$env:ZHU_YE_RELEASE_PUBLIC_KEY = '<公钥 hex>'
.\scripts\assemble-release.ps1 -Version <X.Y.Z>
```

脚本行为（`scripts/assemble-release.ps1`，T-094）：

1. 校验发布公钥已设置；签名模式还校验私钥已设置；
2. `cargo clean -p zhu-ye-updater` 后全量 `cargo build --release`（clean 是必须的：
   `option_env!` 的公钥变化不会被增量缓存感知）；
3. 组装 `target/release-assets/<X.Y.Z>/`：
   - `packs/it.zyct med.zyct slang.zyct`（仅分发包进 manifest，`DISTRIBUTABLE_PACK_IDS`；
     base.zyct 随安装包只读交付、en.zyen 是引擎资产，均不进更新源）；
   - `zhu-ye-dict build-manifest` → `sign-manifest`（规范化 JSON + ed25519）→
     `verify-manifest`（逐包哈希/大小复核，发布检查清单 7.4 执行项）；
   - `zhu-ye-ime-<X.Y.Z>.zip`（复用 `package-portable.ps1` 产物改名；发布命名见 T-108）；
   - `SHA256SUMS.txt`（上传核对清单）。

### 步骤 3 — 上传 GitHub Releases 资产

> 正式路径由 CI 自动执行（见步骤 2 提示）；以下命令保留为本地人工发布/补传参考。
> 注意 `manifest.json` 必须与各包同级上传（更新器按 `{base_url}/{pack.file}` 下载）；
> `releases/latest/download/manifest.json` 由此自动可得（客户端默认 URL，见
> `crates/zhu-ye-updater/src/main.rs` 的 `DEFAULT_MANIFEST_URL`）；可先用
> `ZHU_YE_MANIFEST_URL` 覆盖区验证再切默认。

```powershell
gh release create v<X.Y.Z> --title "v<X.Y.Z>" --notes "发布说明（见 CHANGELOG <X.Y.Z> 段）"
gh release upload v<X.Y.Z> target/release-assets/<X.Y.Z>/SHA256SUMS.txt \
    target/release-assets/<X.Y.Z>/zhu-ye-ime-<X.Y.Z>.zip \
    target/release-assets/<X.Y.Z>/ai-zhu-ye-ime-setup-<X.Y.Z>.exe \
    target/release-assets/<X.Y.Z>/packs/it.zyct med.zyct slang.zyct \
    target/release-assets/<X.Y.Z>/packs/manifest.json
```

> exe 安装包为 Inno Setup 编译产物（T-097）：CI 中 `choco install innosetup` +
> `build-setup.ps1 -OutputDir target/release-assets/<ver> -Sha256File …/SHA256SUMS.txt`；
> 载荷与便携 zip 同 staging（`stage-package.ps1` 公共源），哈希计入 SHA256SUMS.txt
> （下载页校验值）。本机可用 `.\scripts\build-setup.ps1` 构建（ISCC 需 Inno Setup 6）。

### 步骤 3.5 — 发布更新源镜像（feed 分发，T-098）

CI 在步骤 3 之后自动执行（`.github/workflows/release.yml` 的 `publish-updates` 步骤）：

- **自动路径**：配置 `ZHU_YE_UPDATES_TOKEN`（`zhu-ye-updates` 仓库 `contents:write`
  细粒度 PAT）后，CI 将三领域包 + manifest 上传到镜像仓库
  `menghun3-cn/zhu-ye-updates` 的 `feed-v<X.Y.Z>` release（`--target <commit sha>`
  追溯），客户端默认 URL（`releases/latest/download/manifest.json`）自动可得
  （feed release **不带 prerelease 标记**，tag 含 `-` 不改变 latest 语义，T-096 §21.1）。
- **缺 PAT**：CI 跳过并告警（不阻塞主发布）；可手动补传：

```powershell
gh release create feed-v<X.Y.Z> --repo menghun3-cn/zhu-ye-updates `
    --target <sha> --notes "竹叶输入法更新源 feed v<X.Y.Z>"
gh release upload feed-v<X.Y.Z> --repo menghun3-cn/zhu-ye-updates `
    target/release-assets/<X.Y.Z>/packs/manifest.json it.zyct med.zyct slang.zyct --clobber
```

发布后按步骤 4 验证默认 URL 的 check/apply/篡改拒绝/回滚（§17.2 双通道已就绪，
见 Agent Note `2026-10-05-updater-e2e-sandbox`）。

### 步骤 4 — 更新源验证（端到端）

在测试机（或验收 VM）上：

1. 检查已内置公钥：`updater status` 不报"未内置发布公钥"；
2. 配置 `online_update: true`（设置窗口"关于与更新"→ 启用，或直接改
   `%APPDATA%\ai-zhu-ye-ime\config.json`）；
3. `updater check` 应报告示例域名包为最新；`updater apply` 应下载、验签、原子替换
   全部 3 个领域包（日志显示 staging → rename 与 `.bak` 备份）；
4. **回滚演练**（验收 FR-020，发布执 行）：把某包替换为篡改字节 → `apply` 必须拒绝；
   把 `form` 目录某包手动改坏 → 恢复 `.bak`。

### 步骤 5 — 发布检查清单收尾（执行项回填）

- [ ] §7.4：`verify-manifest` 输出记录（SHA256SUMS.txt 归档到 `docs/release/` 或发布 PR）；
- [ ] §7.4：把关抽查报告随发布记录（slang 正负样例命中数据 + 把关表版本，`data/artifacts/slang.gate.json`）；
- [ ] §7.4：BY-SA 派生数据许可声明随安装包可见（zip 内 docs/licenses.md 路径核对）；
- [ ] §5：安装/卸载脚本完整回滚再确认（干净机或测试机）；
- [ ] 官网下载页 release 链接实测可下载。

### 步骤 6 — 收尾（AGENTS.md §6）

- 确认 main 已同步回 develop、release 分支已删除、tag 已推送；
- 官网状态行版本号与当前发布版本一致（`site/` 六页 hero-note/footer + agents.txt + llms.txt）；
- todos-list 中发布相关任务记为已完成，发布过程要点记入 Agent Note（与信任链 note 交叉引用）；
- 发布后启动下一轮开发前，重新确认 CHANGELOG `[Unreleased]` 为空。

## 4. 故障预案

| 故障 | 处理 |
| --- | --- |
| 推送/PR 网络抖动 | 重试循环（至多 8 次、间隔 12s）；以 `gh pr view --json state` 为准，忽略 ff 告警 |
| `sign-manifest` 报未设置私钥 | 检查发布环境密钥注入（脚本拒绝无密钥签名）；**不要**把私钥写成命令行参数 |
| 上传后发现 manifest 与包不一致 | 重跑步骤 2 的 `verify-manifest`；不一致则撤销 release 资产并重新上传（tag 已推时先删后重建；禁止覆盖已推 tag） |
| 客户端拒绝更新（验签失败） | 确认构建时公钥注入成功（`updater status`）、manifest 的 `signature.public_key` 与内置公钥一致 |
| 发布后立即发现严重缺陷 | 按 CHANGELOG 惯例在下一版本段记录修复，不新建 tag 覆盖 |
