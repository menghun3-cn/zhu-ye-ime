## 3. 总体架构

新增能力横跨 core（纯算法）与 ime（装配/张罗），TSF 层**零改动**（通讯录只影响候选
内容与顺序，候选窗交互全部复用既有路径）：

- **core `vcard` 模块**：vCard 3.0 子集解析器（纯算法、可测）——行折叠（`\r\n ` 续行）、
  转义（`\\` `\,` `\;` `\n`）、`FN`（姓名）/`N`（结构化姓名）字段提取、检索字段
  **`ORG`/`EMAIL`/`ADR` 提取**（多值按出现顺序 `; ` 拼接，D-20 四源；其余字段如
  `TEL`/`NOTE` 忽略不报错）、未知属性/版本跳过不报错、编码按 UTF-8 与 `CHARSET` 参数
- **core `contacts` 模块**：联系人表 = 姓名 + 检索字段 + 拼音键集合（D-22 全读形）。
  中文姓名/公司名/地址注音复用既有注音管线（kTGHZ2013 + 全拼表校验）；非中文
  （英文名/公司/邮箱）按原文建键（T-102 四源合并去重）
- **core 查询**：`contacts_for_prefix(pinyin_prefix)` 前缀扫描（partition_point 模式），
  命中来源标记 `CandidateSource::Contact`，不参与分数排序（提权位次由协调层决定）
- **ime 装配**：启动读取 config.json 的 `contact_vcards` 路径列表（D-19）→ 导入/加载
  联系人索引到内存；`enable_contact_boost` 语义并入场景8 提权协调层（D-21 同层）
- **配置**：`contact_vcards: [...]`（路径列表）+ 清除 = 配置清空并删导入文件与索引

### 3.1 为什么 vCard 导入（而不是读系统通讯录）

- 零系统 API 依赖：WinRT `Windows.Contacts` 在 Server 2019 上可用性与权限模型复杂，
  Rust 侧接入需 COM/WinRT FFI——直接违反「crates 层零 .NET 约束」与「全部自研可控」
- 确定性可测：vCard 是纯文本文件，解析器输入输出完全确定，可做逐位可复现测试
- 隐私最小化：用户显式导出的文件才进索引，系统通讯录不会"顺带"被读

### 3.2 姓名注音与建键（D-20/D-22；T-102 扩展四源）

- 姓名拆分：`FN` 全名（如 `张三`）优先；无 `FN` 时用 `N` 组件拼接（姓氏+名）
- **检索字段（T-102）**：`ORG`（公司名）`ADR`（地址）`EMAIL`（电邮）各收集全部
  非空值按出现顺序 `; ` 拼接（多部门/多邮箱/多地址不丢）；字段顺序无保证，
  解析收尾统一组装（FN 与 N 并存时以 FN 为准）
- 注音：逐字查内置注音表（kTGHZ2013，运行时静态表 `char_pinyin`，与 `en_words`
  同模式生成+哈希锁定）；多音字（如 `曾` = zeng/ceng、`乐` = le/yue）
  **全部读音形态建键**（D-22）：每键都索引同一联系人，查询任一读音均可命中
- **四源合并（T-102）**：姓名/公司/地址/邮箱各自生成键集后合并去重（同联系人跨源
  同键只一次）；命中任意来源均上屏**姓名**：
  - 中文公司名/地址 → 注音键（`竹叶科技` → zhuyekeji、`北京市` → beijingshi）
  - 邮箱 → 连续小写原形（`bob@acme.com` → bobacmecom，`@`/`.` 等符号被跳过），
    输入邮箱用户名段前缀即命中；`@` 后域名段不独立成键
  - 非中文字符：保留原文作附加键（如英文名 `Alice` → alice、英文公司 `Alice Tech`
    → alicetech）
- **简拼键（FR-037）**：索引构建期从每个全拼键按标准音节表切分、取每音节首字母派生
  （如 `zhangsan` → `zs`、`竹叶科技` → `zykj`）；多音有多形态时各派生
  （`zengzi`→`zz`、`cengzi`→`cz`）；英文原形键/单音节键不派生。**不修改 FR-023
  词典缩写路径**——联系人简拼是索引原生键，`zs` 直接在联系人索引命中（行为等价：
  FR-023 判定用于词典，联系人索引自带简拼）
- 联系人数上限：索引容量预算 ≤10k 联系人（NFR-006 常驻内存预算内），导入超限截断并用
  日志提示（不静默丢弃——记录导入统计）

### 3.3 提权协调层（D-21 与 D-13 同层）

候选清单顺序统一为：

```
基础候选
└─ 提权候选（领域提权 D-13 / 联系人提权 D-21，同一插入点、按来源顺序）
└─ 追加：缩写组 → 英文组 → emoji 队尾
```

- 领域与联系人**同时命中**时：联系人候选排在领域候选之后（联系人=用户明确导入的
  更高置信数据）——规则写死保证确定性（同一输入两次同序）
- 无联系人命中时清单与现版逐位一致（T-050 不漂移基线）

## 4. 接口设计（草案）

core（新增，纯算法；**接口已按实现校准**——注音由 core 内置表完成，无回调注入）：

```
pub struct VCardContact {
    pub name: String,      // 姓名（FN 或 N 拼接）
    pub org: String,       // 组织（ORG 多值 `; ` 拼接，T-102）
    pub email: String,     // 电邮（EMAIL 多值 `; ` 拼接，T-102）
    pub address: String,   // 地址（ADR 多值 `; ` 拼接，T-102）
    pub keys: Vec<String>, // 拼音键集合（索引构建阶段填充）
}
pub fn VCardContact::new(name) -> VCardContact; // 仅姓名构造（附加字段空串）
pub fn parse_vcard(input: &str) -> Result<Vec<VCardContact>, VCardError>;
    // vCard 3.0 子集：BEGIN:VCARD 段解析、FN/N/ORG/EMAIL/ADR 提取、其余字段忽略、
    // 行折叠与转义
pub struct ContactIndex { /* 按 key 前缀排序的静态表（Ordinal） */ }
pub fn build_contact_index(contacts: &[VCardContact]) -> ContactIndex;
    // core 内置 kTGHZ2013 注音表按字注音（全读形，D-22）+ 简拼键派生（FR-037）；
    // 姓名/组织/地址/电邮四源键合并去重（T-102）；键唯一有序（partition_point 依赖）
fn contact_keys(contact: &VCardContact) -> Vec<String>;
    // 单联系人四源键合并（排序去重）
pub fn abbreviation_key(name_key: &str, table: &SyllableTable) -> Option<String>;
    // 全拼键 → 音节首字母简拼键（英文原形键/单音节键返回 None）
pub fn contact_candidates(index: &ContactIndex, pinyin_prefix: &str, cap: usize) -> Vec<Candidate>;
    // 前缀扫描命中（全拼键/简拼键同一索引）→ candidate{ text: 姓名, source: Contact }
```

ime 引擎（装配/组装；**接口已按实现校准**——无独立开关，挂载即生效）：

```
pub fn with_contacts(self, index: ContactIndex) -> Self;   // 启动导入（D-19 配置触发）
pub fn clear_contacts(&mut self);                          // 清除索引（FR-038）
// refresh_candidates 内：提权协调层统一插入（D-21，与领域同层、排在其后）
```

配置（`pack_config` 扩展，向后兼容）：

```

```

## 5. 测试策略

core 单测（新增，确定性）：
- vCard 解析：标准 FN 片段 / 行折叠 / 转义序列 / 未知字段跳过 / 无 FN 用 N 拼接 /
  损坏输入返回错误 / 编码参数（CHARSET）
- 检索字段提取（T-102）：ORG/EMAIL/ADR 各自提取与缺省空串 / 多值 `; ` 拼接 /
  空值忽略与参数样式 / FN 在字段后不丢失 / 组前缀与转义
- 注音建键：单音字 / 多音字全形态（D-22）/ 英文名原形键 / 键有序无重复
- 四源建键（T-102）：中文公司名注音命中 / 公司名简拼 / 英文公司原形 /
  邮箱用户名前缀命中（域名段不独立成键）/ 地址注音命中 / 四源同键去重
- 简拼键派生：`zs` 前缀命中张三 / 多音简拼多形态（`zz`/`cz` 均命中曾子）/
  英文名不派生
- 查询：前缀命中 / 未命中 / 上限截断 / 确定性（同一索引两次查询逐位一致）

- 清除后候选消失、输入回基线
- 领域+联系人同时命中 → 联系人排在领域之后（协调层规则）
- 四源检索（T-102）：`zhuye`（公司）/`bob`（邮箱）/`beijing`（地址）均命中张三

## 6. 性能与隐私

- 查询开销：联系人索引为小表（≤10k），前缀扫描与英文表同阶；提权协调层只重组清单
  不重算分数；验收 12.2 单帧 ≤2ms
- 导入开销：1000 条 vCard ≤1s（一次性操作）；解析与注音构建在启动路径外（异步或懒加载
  待定，见风险）
- 隐私：联系人内容只存用户数据目录运行时文件；**不写入词典产物/日志/提交**；
  清除能力删除导入副本与索引（FR-038）
- 基准：联系人候选只在命中时生效；T-057 eval 集逐位不回退（验收 12.2 复跑记录）

## 8. 风险与备选

- **编码**：vCard 常见 UTF-8 与 GBK `CHARSET=GB2312` 变体 → 解析器支持 `CHARSET` 参数，
  GBK 转码在 core 不可带 ICU/系统码页时仅记录并跳过（首批只保证 UTF-8，文档记录）
- **注音缺失字**：kTGHZ2013 未收的生僻字 → 该字不建键（联系人仍可按其他键命中）；
  日志记录导入统计而非静默
- **启动开销**：大 vcf 导入在启动路径上 → 导入分片（≤2k 条/批），首批不引入异步
  （确定性优先）；若实测超预算再评估懒加载
- **与领域提权顺序**：联系人/领域同时命中顺序固定（联系人前），如体验不佳可后续加
  配置项调整（隐私与可回退原则下不改变默认确定性）
