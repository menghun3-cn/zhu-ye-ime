## 3. 总体架构

新增能力横跨 core（纯算法）与 ime（装配/张罗），TSF 层**零改动**（通讯录只影响候选
内容与顺序，候选窗交互全部复用既有路径）：

- **core `vcard` 模块**：vCard 3.0 子集解析器（纯算法、可测）——行折叠（`\r\n ` 续行）、
  转义（`\\` `\,` `\;` `\n`）、`FN`（姓名）/`N`（结构化姓名）字段提取、`ORG` 忽略
  （D-20 仅姓名）、未知属性/版本跳过不报错、编码按 UTF-8 与 `CHARSET` 参数
- **core `contacts` 模块**：联系人表 = 姓名 + 拼音键集合（D-22 全读形）。中文姓名注音
  复用既有注音管线（kTGHZ2013 + 全拼表校验）；非中文姓名（英文名/数字）按原文建键
- **core 查询**：`contacts_for_prefix(pinyin_prefix)` 前缀扫描（partition_point 模式），
  命中来源标记 `CandidateSource::Contact`，不参与分数排序（提权位次由协调层决定）
- **ime 装配**：启动读取 config.json 的 `contact_vcards` 路径列表（D-19）→ 导入/加载
  联系人索引到内存；`enable_contact_boost` 语义并入场景8 提权协调层（D-21 同层）
- **配置**：`contact_vcards: [...]`（路径列表）+ 清除 = 配置清空并删导入文件与索引

### 3.1 为什么 vCard 导入（而不是读系统通讯录）

- 零系统 API 依赖：WinRT `Windows.Contacts` 在 Server 2019 上可用性与权限模型复杂，
  Rust 侧接入需 COM/WinRT FFI——直接违反「crates 层零 .NET 约束」与「全部自研可控」
- 确定性可测：vCard 是纯文本文件，解析器输入输出完全确定，可做逐位可复现测试
- 隐私最小化：用户显式导出的文件才进索引，系统通讯录不会"顺带"被读

### 3.2 姓名注音与建键（D-20/D-22）

- 姓名拆分：`FN` 全名（如 `张三`）优先；无 `FN` 时用 `N` 组件拼接（姓氏+名）
- 注音：逐字查既有注音表（kTGHZ2013）；多音字（如 `曾` = zeng/ceng、`乐` = le/yue）
  **全部读音形态建键**（D-22）：每键都索引同一联系人，查询任一读音均可命中
- 非中文字符：保留原文作附加键（如英文名 `Alice` → alice）
- 联系人数上限：索引容量预算 ≤10k 联系人（NFR-006 常驻内存预算内），导入超限截断并用
  日志提示（不静默丢弃——记录导入统计）

### 3.3 提权协调层（D-21 与 D-13 同层）

候选清单顺序统一为：

```
基础候选
└─ 提权候选（领域提权 D-13 / 联系人提权 D-21，同一插入点、按来源顺序）
└─ 追加：缩写组 → 英文组 → emoji 队尾
```

- 领域与联系人**同时命中**时：联系人候选排在领域候选之后（联系人=用户明确导入的
  更高置信数据）——规则写死保证确定性（同一输入两次同序）
- 无联系人命中时清单与现版逐位一致（T-050 不漂移基线）

## 4. 接口设计（草案）

core（新增，纯算法）：

```
pub struct VCardContact { pub name: String, pub keys: Vec<String> }   // 姓名 + 拼音键集合
pub fn parse_vcard(input: &str) -> Result<Vec<VCardContact>, VCardError>;
    // vCard 3.0 子集：BEGIN:VCARD 段解析、FN/N 提取、其余字段忽略、行折叠与转义
pub struct ContactIndex { /* 按 key 前缀排序的静态表（Ordinal） */ }
pub fn build_contact_index(contacts: &[VCardContact], annotate: &dyn Fn(&str) -> Vec<String>) -> ContactIndex;
    // annotate = 姓名注音（全读形，D-22）；键唯一有序（partition_point 依赖）
pub fn contact_candidates(index: &ContactIndex, pinyin_prefix: &str, cap: usize) -> Vec<Candidate>;
    // 前缀扫描命中 → candidate{ text: 姓名, source: Contact }
```

ime 引擎（装配/组装）：

```
pub fn set_contact_vcards(&mut self, paths: &[PathBuf]);   // 启动导入（D-19 配置触发）
pub fn clear_contacts(&mut self);                          // 清除索引+副本（FR-038）
// refresh_candidates 内：提权协调层统一插入（D-21）
```

配置（`pack_config` 扩展，向后兼容）：

```
"contact_vcards": ["C:\\Users\\x\\contacts.vcf"]           // 缺失=空列表（无联系人）
```

## 5. 测试策略

core 单测（新增，确定性）：
- vCard 解析：标准 FN 片段 / 行折叠 / 转义序列 / 未知字段跳过 / 无 FN 用 N 拼接 /
  损坏输入返回错误 / 编码参数（CHARSET）
- 注音建键：单音字 / 多音字全形态（D-22）/ 英文名原形键 / 键有序无重复
- 查询：前缀命中 / 未命中 / 上限截断 / 确定性（同一索引两次查询逐位一致）

## 6. 性能与隐私

- 查询开销：联系人索引为小表（≤10k），前缀扫描与英文表同阶；提权协调层只重组清单
  不重算分数；验收 12.2 单帧 ≤2ms
- 导入开销：1000 条 vCard ≤1s（一次性操作）；解析与注音构建在启动路径外（异步或懒加载
  待定，见风险）
- 隐私：联系人内容只存用户数据目录运行时文件；**不写入词典产物/日志/提交**；
  清除能力删除导入副本与索引（FR-038）
- 基准：联系人候选只在命中时生效；T-057 eval 集逐位不回退（验收 12.2 复跑记录）

## 8. 风险与备选

- **编码**：vCard 常见 UTF-8 与 GBK `CHARSET=GB2312` 变体 → 解析器支持 `CHARSET` 参数，
  GBK 转码在 core 不可带 ICU/系统码页时仅记录并跳过（首批只保证 UTF-8，文档记录）
- **注音缺失字**：kTGHZ2013 未收的生僻字 → 该字不建键（联系人仍可按其他键命中）；
  日志记录导入统计而非静默
- **启动开销**：大 vcf 导入在启动路径上 → 导入分片（≤2k 条/批），首批不引入异步
  （确定性优先）；若实测超预算再评估懒加载
- **与领域提权顺序**：联系人/领域同时命中顺序固定（联系人前），如体验不佳可后续加
  配置项调整（隐私与可回退原则下不改变默认确定性）
